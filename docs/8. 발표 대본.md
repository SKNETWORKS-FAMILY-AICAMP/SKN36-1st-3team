# 🚗 SAFE 발표 대본

> **발표 방향**
>
> 기술 구현 중심으로 설명  
> **데이터 수집 → 전처리 → DB → 웹 구현 → 시각화 → 미래전망 → 정책 활용**

---

# 1. 🚗 표지

## SAFE  
### Safe-driving Analytics & Forecasting Engine

안녕하세요.  
저희가 진행한 프로젝트는 **SAFE, Safe-driving Analytics & Forecasting Engine**입니다.

SAFE는 고령운전자와 관련된 **인구, 자동차, 교통사고, 정책 데이터**를 통합하여  
현재 교통안전 현황을 분석하고, 향후 변화를 전망할 수 있도록 만든 서비스입니다.

저는 이번 발표에서

**데이터 수집 → 데이터 전처리 → 데이터베이스 구축 → 웹 시각화 → 미래 전망**

까지 **기술적인 구현 과정**을 중심으로 설명드리겠습니다.

---

# 2. 📌 프로젝트 한눈에 보기

먼저 전체적인 프로젝트 흐름입니다.

저희는 공공데이터를 수집한 뒤,  
분석 가능한 형태로 전처리하고 **MySQL에 적재**했습니다.

이후 데이터를 분석하고 시각화하여 웹 서비스로 제공하고,  
마지막으로 과거 데이터를 활용한 **미래 전망 기능**까지 구현했습니다.

데이터는 크게

- **인구**
- **자동차**
- **교통사고**
- **제도**
- **FAQ**

총 **5개 영역**으로 구성했습니다.

SAFE는 단순 통계 조회에서 끝나는 것이 아니라,

> **현재 현황 파악 → 추세 분석 → 미래 전망 → 정책 대응**

까지 이어지는 흐름을 만드는 것을 목표로 했습니다.

주요 사용자는  
**지자체 교통정책 담당자 및 교통안전 담당자**로 설정했습니다.

# 3. 🏗️ 전체 시스템 아키텍처

전체 시스템 구조는 다음과 같습니다.

먼저

**TAAS, KOSIS, 행정안전부, 경찰청, 국토교통부**

등에서 공공데이터를 수집했습니다.

원본 데이터는 대부분 **Excel 또는 CSV** 형태였고,  
이를 `pandas`를 이용해 전처리했습니다.

전처리된 데이터는 **MySQL**에 저장하고,

- `SQLAlchemy`
- `PyMySQL`

을 이용해 Python과 데이터베이스를 연결했습니다.

이후 `pandas`, `NumPy`를 이용해 필요한 지표를 계산하고,  
`Streamlit + Plotly`를 이용해 분석 결과를 사용자에게 제공합니다.

### 핵심 흐름

```text
수집
 ↓
전처리
 ↓
저장
 ↓
분석
 ↓
시각화
 ↓
서비스 제공
```

# 4. 📚 데이터 수집 — 설계 순서

데이터 수집에서 중요하게 생각했던 점은  
**데이터부터 무작정 수집하지 않았다는 것**입니다.

먼저 서비스에서 제공할 메뉴를 정의했습니다.

- **인구** → 지역별 인구 및 고령화 현황
- **자동차** → 자동차 등록, 운전면허, 자진반납
- **교통사고** → 연령, 시간대, 기상상태, 지역별 사고
- **제도** → 고령운전자 관련 정책 비교
- **FAQ** → 교통안전 관련 정보 조회

그다음 각 메뉴에서 필요한 분석을 정하고,  
그 분석에 필요한 데이터를 **역으로 찾아 수집**했습니다.

### 수집 설계 흐름

```text
서비스 메뉴 정의
        ↓
분석 목적 설정
        ↓
필요 데이터 선정
        ↓
공공데이터 수집
```

# 5. 📚 데이터 출처

데이터는 한 기관에서 가져온 것이 아니라  
여러 공공기관의 데이터를 조합했습니다.

- **인구** → e-나라지표, 행정안전부
- **자동차·운전면허** → 국토교통부, KOSIS, 경찰청
- **교통사고** → TAAS
- **제도** → 도로교통공단 및 지역별 정책자료

TAAS 데이터는 특히

- 연령
- 시간대
- 기상상태
- 지역
- 사고유형

등 여러 기준으로 세분화해 사용했습니다.

여기서 가장 큰 문제는  
**기관마다 데이터 형식이 모두 다르다는 점**이었습니다.

그래서 단순 수집보다  
이 데이터를 동일한 기준에서 분석할 수 있도록 **표준화하는 과정이 핵심**이었습니다.

# 6. ⚙️ 데이터 전처리 파이프라인

다음은 데이터 전처리 과정입니다.

먼저 Excel이나 CSV 파일을 불러와  
**원본의 헤더 구조를 확인**했습니다.

이후 순서대로

1. 결측치 및 병합 셀 처리
2. 합계·소계 등 불필요 행 제거
3. 컬럼명 및 문자열 표준화
4. Wide Format → Long Format 변환
5. 연도·지역·연령·시간대 정보 추출
6. 숫자 및 날짜 타입 변환
7. Pivot 및 파생지표 생성
8. 최종 결과 검증

을 진행했습니다.

최종적으로 서로 다른 데이터를

> **지역 · 연도 · 연령 · 시간대**

라는 공통 분석 기준으로 맞췄습니다.

# 7. ⚙️ 전처리 실전 사례

실제 전처리 과정에서는 몇 가지 문제가 반복적으로 발생했습니다.

## ① Excel 병합 셀

pandas로 읽으면 병합된 셀의 일부가 `NaN`으로 들어옵니다.

그래서

```python
ffill()
```

을 이용해 상위 값을 아래 행까지 복원했습니다.

---

## ② Wide Format

원본 데이터는 다음처럼  
연도가 각각 컬럼으로 존재하는 경우가 많았습니다.

```text
지역 | 2021 | 2022 | 2023
서울 | 100  | 110  | 120
```

이 구조는 새로운 연도가 추가될 때마다 컬럼이 증가합니다.

그래서 `melt()`를 이용해

```text
지역 | 연도 | 값
서울 | 2021 | 100
서울 | 2022 | 110
서울 | 2023 | 120
```

형태의 **Long Format**으로 변경했습니다.

이렇게 하면 DB에서

- `WHERE year`
- `GROUP BY year`

와 같은 조회가 훨씬 쉬워집니다.

---

## ③ CSV 인코딩

기관마다 CSV 인코딩 방식이 달라  
한글이 깨지는 문제가 있었습니다.

그래서

```text
utf-8-sig
cp949
utf-8
euc-kr
```

등 여러 인코딩에 대응하도록 처리했습니다.

---

## ④ 사고 심각도 데이터

TAAS 연령대별 사고 데이터는 처음에는  
단순 사고건수만 사용하려 했습니다.

하지만 실제 분석에서는  
**사고건수만으로 사고 심각도를 판단하기 어렵다**고 판단했습니다.

그래서 최종적으로

- `accidents`
- `deaths`
- `injuries`

세 가지 지표로 재구성했습니다.

# 8. 🗄️ DB 설계 — SQLite → MySQL

데이터베이스는 처음부터 MySQL을 사용한 것은 아닙니다.

초기 개발 단계에서는  
빠르게 기능을 구현하고 테스트하기 위해 **SQLite**를 사용했습니다.

SQLite는 별도의 서버 설정 없이 바로 사용할 수 있기 때문에  
초기 프로토타입에는 적합했습니다.

하지만 프로젝트가 진행되면서

- 데이터 종류 증가
- 테이블 수 증가
- 여러 페이지에서 동일 데이터 조회
- 통합 관리 필요

가 발생했습니다.

그래서 파일 단위로 관리하는 것보다  
하나의 데이터베이스에서 체계적으로 관리하는 것이 필요하다고 판단했습니다.

최종적으로

> **SQLite → MySQL**

로 전환했습니다.

그리고

- `SQLAlchemy`
- `PyMySQL`

을 이용해 DB 연결 구조를 구성했습니다.

현재 데이터 규모만 보면 SQLite로도 구현은 가능하지만,  
**통합 관리와 향후 확장성을 고려한 선택**이었습니다.

---

# 9. 🗄️ DB 적재 구조

데이터 적재 과정도 반복해서 사용할 수 있도록 구성했습니다.

먼저

> **전처리 함수 ↔ DB 테이블**

을 매핑했습니다.

그 다음

```text
테이블 존재 여부 확인
        ↓
CREATE TABLE IF NOT EXISTS
        ↓
기존 데이터 TRUNCATE
        ↓
최신 전처리 데이터 적재
        ↓
적재 결과 검증
```

순서로 진행했습니다.

실제 적재는

```python
DataFrame.to_sql()
```

을 사용했습니다.

그리고 데이터를 한 번에 모두 넣는 대신  
`chunksize`를 설정해 일정 단위로 나누어 INSERT하도록 했습니다.

마지막에는

- 적재 행 수
- 컬럼 수
- 오류 로그

를 확인했습니다.

현재는 **전체 재적재 방식**이지만,  
향후 데이터 규모가 커지면  
**신규·변경 데이터만 처리하는 증분 적재 방식**으로 개선할 수 있습니다.

# 10. 📂 프로젝트 폴더 구조

코드 역시 데이터 흐름에 맞춰 역할별로 분리했습니다.

### `data`

수집한 원본 데이터 저장

### `analyze`

각 데이터별 전처리 담당

### `database`

MySQL 연결 및 데이터 적재 담당

### `data_repository`

Streamlit에서 필요한 데이터를 DB에서 조회

### `models`

시계열 분석 및 미래 전망 로직

### `streamlit`

최종 사용자 웹 화면 구현

### 전체 흐름

```text
원본 데이터
   ↓
전처리
   ↓
DB 적재
   ↓
데이터 조회
   ↓
분석 및 예측
   ↓
웹 서비스
```

즉 **실제 폴더 구조도 데이터 파이프라인과 동일한 흐름**으로 구성했습니다.

# 12. 📊 시각화 기법 선택 기준

시각화에서는 모든 데이터를 같은 그래프로 표현하지 않았습니다.

**분석 목적에 따라 차트 종류를 선택했습니다.**

### KPI Metric

핵심 수치를 빠르게 확인

### Line Chart

연도·월별 변화처럼  
시간에 따른 **추세 분석**

### Bar Chart

지역·연령 등  
항목별 **규모 및 순위 비교**

### Heatmap

월·시간대처럼  
두 기준에서 사고가 집중되는 구간 확인

### Choropleth Map

지역별 사고 수준의  
**공간적 차이 비교**

핵심은 그래프를 다양하게 만드는 것이 아니라

> **사용자가 무엇을 비교해야 하는가**

를 기준으로 시각화 방식을 선택했다는 점입니다.

# 13. 🚨 교통사고 심각도 분석

교통사고 분석 과정에서  
한 가지 중요한 문제를 발견했습니다.

> **사고가 많다는 것과 사고가 심각하다는 것은 다르다.**

처음에는 사고건수 중심으로 분석했지만,  
이것만으로는 실제 피해 정도를 확인하기 어려웠습니다.

그래서 원본 데이터에서

- 사고건수
- 사망자
- 부상자

데이터를 함께 활용했습니다.

그리고 추가적으로

### 사고 100건당 사망자

사고 규모를 보정한 **치명도 비교**

### 사고 1건당 부상자

사고 1건당 발생하는 **평균 인적 피해 비교**

를 계산했습니다.

이를 통해

> **사고가 많은 지역**

과

> **사고 발생 시 피해가 큰 지역**

을 구분해서 볼 수 있도록 구현했습니다.

# 14. 🔮 미래 전망 분석

다음은 미래 전망 기능입니다.

SAFE에서는 크게 **두 가지 방식**을 사용했습니다.

---

## ① Linear Trend

과거 연도별 데이터의 증가·감소 흐름을  
직선 형태로 모델링합니다.

그리고

> **현재 추세가 앞으로도 지속된다**

고 가정하여 미래 값을 전망합니다.

---

## ② Proxy Growth Scenario

직접적인 장기 시계열 데이터가 부족한 경우  
관련성이 높은 다른 지표의 변화율을 **대리변수, Proxy**로 사용하는 방식입니다.

예를 들어 고령운전자 관련 데이터가 부족한 경우

> **고령인구 변화율**

을 이용해 미래 변화 시나리오를 구성했습니다.

# 15. 🔮 왜 ARIMA · Prophet · LSTM이 아니었는가

복잡한 예측 모델을 사용하지 않은 가장 큰 이유는  
**현재 확보한 데이터의 시계열 길이**입니다.

주요 데이터가

> **2021년 ~ 2025년**

정도의 짧은 연 단위 데이터입니다.

---

## ARIMA

과거 시점의 값과 예측 오차를 활용하는  
대표적인 시계열 분석 방법입니다.

하지만 충분한 관측치가 필요합니다.

---

## Prophet

장기간의 일별·월별 데이터에서

- 추세
- 계절성

을 분석하는 데 강점이 있습니다.

하지만 현재 SAFE 데이터는 연 단위라  
장점을 충분히 활용하기 어렵습니다.

---

## LSTM

시계열의 복잡한 패턴을 학습할 수 있는  
딥러닝 모델입니다.

하지만 많은 학습 데이터가 필요하고,  
현재 데이터에서는 **과적합 위험**이 있습니다.

---

따라서 복잡한 모델 자체를 사용하는 것보다

> **현재 데이터 수준에서 설명 가능하고 해석하기 쉬운 방법**

을 선택하는 것이 적절하다고 판단했습니다.

그리고 SAFE의 결과는

> **미래를 정확히 단정하는 예측값이 아니라  
> "현재 추세가 지속된다면 어떻게 변화할 것인가"를 보여주는 전망치**

입니다.

---

# 16. 🎯 정책 대응 우선순위

미래 전망 결과는  
정책 대응 우선순위 분석에도 활용했습니다.

단순히 현재 사고건수가 높은 지역만 보는 것이 아니라

- 현재 사고 수준
- 미래 사고 변화
- 고령인구 변화

를 함께 고려했습니다.

이를 통해

> **향후 정책 검토가 상대적으로 먼저 필요한 지역**

을 탐색할 수 있도록 했습니다.

다만 중요한 점은

> **이 순위가 절대적인 위험 순위는 아니라는 것**

입니다.

SAFE 데이터와 분석 가정에 따른  
**상대적인 정책 검토 우선순위**입니다.

실제 정책 결정에서는

- 교통환경
- 지역 특성
- 기존 정책

등 추가 요소도 함께 고려해야 합니다.

# 17. 🔧 주요 트러블슈팅

개발 과정에서는 여러 기술적 문제가 발생했습니다.

### Excel 병합 셀

`NaN` 발생  
→ `ffill()`로 해결

### CSV 인코딩

기관별 인코딩 차이  
→ 다중 인코딩 처리

### Wide Format

연도별 분석 및 확장 불편  
→ `melt()`로 Long Format 변환

### 합계 행

중복 집계 발생  
→ 전처리 과정에서 사전 제거

### DataFrame ↔ DB 컬럼 불일치

적재 오류 발생  
→ 컬럼명 표준화

### 재적재 데이터 중복

→ `TRUNCATE` 후 최신 데이터 적재

### 미래 전망 데이터 부족

→ Linear Trend / Proxy Scenario 적용

### SQLite 관리 구조

데이터·테이블 증가  
→ MySQL 전환

이 과정에서 단순히 화면만 수정한 것이 아니라

> **원본 데이터 → 전처리 → DB 구조 → 웹 화면**

까지 전체 흐름을 다시 확인하고 수정했습니다.
